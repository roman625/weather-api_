# Описание методов и стуктуры задания

## 1. Конфигурация и управление настройками

### Класс `Settings`
Наследуется от `pydantic_settings.BaseSettings`, что позволяет гибко управлять конфигурацией приложения через переменные окружения или файл `.env`.

**Атрибуты:**
*   `app_host` (str, по умолчанию `"127.0.0.1"`): IP-адрес, на котором будет запущен сервер.
*   `app_port` (int, по умолчанию `8000`): Порт сервера.
*   `open_meteo_url` (str): Эндпоинт внешнего API (Open-Meteo) для получения метеорологических данных.
*   `db_file` (str, по умолчанию `"weather.db"`): Путь к файлу базы данных SQLite.
*   `update_interval_seconds` (int, по умолчанию `900`): Интервал (в секундах) для фонового обновления прогнозов (15 минут).
*   `request_timeout` (float, по умолчанию `10.0`): Таймаут (в секундах) для сетевых запросов к внешнему API.

**Конфигурация (`model_config`):**
Использует `ConfigDict` для указания пути к файлу `.env` и кодировки `utf-8`, обеспечивая безопасное хранение секретов и настроек вне кода.

## 2. Логирование

**Настройка `logging`:**
Инициализируется базовая конфигурация логгера на уровне `INFO`. Формат сообщений включает временную метку, уровень логирования, имя логгера и само сообщение. Создается специализированный логгер `"weather_api"` для отслеживания событий приложения.

## 3. Работа с базой данных (SQLite)

### Функция `get_db()`
*   **Назначение:** Генератор, реализующий паттерн внедрения зависимостей (Dependency Injection) для FastAPI.
*   **Логика:** 
    1. Устанавливает синхронное соединение с SQLite. Параметр `check_same_thread=False` критичен для использования в асинхронном контексте FastAPI, так как позволяет передавать объект соединения между потоками.
    2. Устанавливает `row_factory = sqlite3.Row`, что позволяет обращаться к результатам запросов по имени столбца (как к словарю), а не только по индексу.
    3. Возвращает объект соединения (`yield conn`).
    4. В блоке `finally` гарантируется закрытие соединения после завершения обработки HTTP-запроса.

### Функция `init_db()`
*   **Назначение:** Инициализация и миграция схемы базы данных при старте приложения.
*   **Логика:** Создает три таблицы, если они еще не существуют (`CREATE TABLE IF NOT EXISTS`):
    1.  **`users`**: Таблица пользователей. Поля: `id` (первичный ключ), `username` (уникальное текстовое поле), `created_at` (временная метка).
    2.  **`cities`**: Таблица отслеживаемых городов. Поля: `id`, `user_id` (внешний ключ к `users` с каскадным удалением `ON DELETE CASCADE`), `name`, `latitude`, `longitude`, `created_at`. Имеет составное уникальное ограничение `UNIQUE(user_id, name)`, предотвращающее дублирование городов у одного пользователя.
    3.  **`forecasts`**: Таблица почасовых прогнозов. Поля: `city_id` (внешний ключ к `cities`), `forecast_date`, `forecast_time`, `temperature`, `humidity`, `wind_speed`, `precipitation`, `updated_at`. Составной первичный ключ `(city_id, forecast_date, forecast_time)` гарантирует уникальность записи для конкретного часа.

## 4. Pydantic-модели (Схемы данных)

Используются для строгой валидации, сериализации и десериализации данных.

1.  **`CurrentWeatherResponse`**: Схема ответа для текущей погоды. Содержит координаты, температуру, скорость ветра, давление и время наблюдения.
2.  **`UserCreateRequest`**: Схема запроса для регистрации. Валидирует `username` (длина от 3 до 50 символов).
3.  **`UserResponse`**: Схема ответа при регистрации (содержит `user_id` и `username`).
4.  **`CityTrackRequest`**: Схема запроса для добавления города. Валидирует `city_name` (1-100 символов), `latitude` (от -90 до 90), `longitude` (от -180 до 180).
5.  **`CityResponse`**: Схема ответа со списком городов (название, широта, долгота).

## 5. Жизненный цикл приложения (Lifespan)

### Асинхронный генератор `lifespan(app: FastAPI)`
*   **Назначение:** Управление ресурсами при запуске и остановке приложения (современная замена `@app.on_event`).
*   **Логика:**
    1.  **Startup (до `yield`)**: Вызывает `init_db()` для подготовки БД. Создает асинхронную задачу `asyncio.create_task(update_forecasts_background_task())` для запуска фонового обновления.
    2.  **Shutdown (после `yield`)**: Вызывает `task.cancel()` для корректной остановки фоновой задачи при завершении работы сервера, предотвращая утечки ресурсов и "зависание" процесса.

## 6. Фоновые задачи и интеграция с внешним API

### Функция `update_forecasts_background_task()`
*   **Назначение:** Периодическое обновление прогнозов для всех городов в базе.
*   **Логика:**
    1.  Работает в бесконечном цикле `while True`.
    2.  Приостанавливает выполнение на `settings.update_interval_seconds`.
    3.  Делает синхронную выборку всех городов из БД.
    4.  Инициализирует `httpx.AsyncClient` и в цикле вызывает `fetch_and_save_forecast` для каждого города.
    5.  **Отказоустойчивость**: Ошибки при обновлении конкретного города перехватываются и логируются, не прерывая цикл для остальных городов.

### Функция `fetch_and_save_forecast(client, city_id, lat, lon)`
*   **Назначение:** Загрузка и сохранение почасового прогноза.
*   **Логика:**
    1.  Формирует параметры запроса к Open-Meteo (запрос hourly-данных: температура, влажность, ветер, осадки на 1 день).
    2.  Выполняет асинхронный GET-запрос. При ошибке HTTP выбрасывает исключение (`raise_for_status()`).
    3.  Парсит JSON-ответ, извлекая массивы времени и метрик.
    4.  **Транзакция БД**: 
        *   Сначала удаляет старые записи прогноза для данного `city_id` и текущей даты (`DELETE`).
        *   Формирует кортежи данных, разделяя время на дату и час.
        *   Выполняет пакетную вставку (`executemany`) новых записей, что значительно быстрее, чем вставка по одной строке.

## 7. Эндпоинты API (REST API)

### 7.1. `POST /users/register`
*   **Назначение:** Регистрация нового пользователя.
*   **Параметры:** Тело запроса `UserCreateRequest`.
*   **Логика:** Пытается выполнить `INSERT`. Если `username` уже существует, SQLite выбросит `IntegrityError`, который перехватывается, и клиенту возвращается статус `409 Conflict`. При успехе возвращается `201 Created` с данными пользователя.

### 7.2. `GET /weather/current`
*   **Назначение:** Получение текущей погоды по координатам (без сохранения в БД).
*   **Параметры:** Query-параметры `latitude` и `longitude` (с валидацией диапазонов).
*   **Логика:** Делает прямой запрос к Open-Meteo с параметром `current`. Маппит полученные данные в `CurrentWeatherResponse`. При сетевых ошибках (`httpx.RequestError`) возвращает `502 Bad Gateway`.

### 7.3. `POST /cities/track`
*   **Назначение:** Добавление города в отслеживание.
*   **Параметры:** Query `user_id`, тело `CityTrackRequest`.
*   **Логика:**
    1.  Проверяет существование пользователя (возвращает `404`, если не найден).
    2.  Нормализует имя города (lowercase, strip).
    3.  Выполняет **UPSERT** (`INSERT ... ON CONFLICT DO UPDATE`): если город уже есть, обновляет координаты; если нет — создает. Это обеспечивает атомарность и идемпотентность.
    4.  Сразу после сохранения вызывает `fetch_and_save_forecast`, чтобы пользователь мог сразу получить прогноз, не дожидаясь фоновой задачи.

### 7.4. `GET /cities`
*   **Назначение:** Получение списка отслеживаемых городов пользователя.
*   **Параметры:** Query `user_id`.
*   **Логика:** Выполняет `SELECT` из `cities`, маппит результаты в список `CityResponse`.

### 7.5. `GET /weather/city/{city_name}`
*   **Назначение:** Получение прогноза на конкретное время.
*   **Параметры:** Path `city_name`, Query `user_id`, Query `time` (формат ЧЧ:ММ), Query `params` (список запрашиваемых метрик, по умолчанию `["temperature"]`).
*   **Логика:**
    1.  **Валидация формата времени**: Проверяет длину строки и наличие двоеточия.
    2.  **Проверка прав**: Ищет город в БД, убеждаясь, что он принадлежит указанному `user_id`.
    3.  **Поиск данных**: Ищет прогноз в `forecasts` на сегодняшнюю дату и указанное время.
    4.  **Динамический ответ**: Формирует JSON-словарь, добавляя в него только те метрики, которые были запрошены в параметре `params`. Это снижает объем передаваемых данных.

Инициализирует и запускает ASGI-сервер `uvicorn`, передавая ему объект `app`, а также хост и порт из конфигурации `settings`.

# Тестирование

Тестовый набор реализован в файле `test_script.py` с использованием фреймворка **pytest** и стандартного клиента тестирования FastAPI (`TestClient`). 

Все тесты являются **юнит-тестами**, что означает полную изоляцию тестируемой бизнес-логики от внешних зависимостей и состояния файловой системы:

---

## 1. Команды для запуска тестов

### 1.1. Установка зависимостей
Перед запуском убедитесь, что в вашем виртуальном окружении установлены необходимые библиотеки:

```bash
pip install pytest httpx fastapi pydantic pydantic-settings
```

### 1.2. Запуск тестового набора

Базовая команда для запуска всех тестов с подробным выводом:

```bash
pytest test_script.py -v
```


## 2. Тестовая инфраструктура

### 2.1. Фикстура `setup_test_db` (autouse)
*   **Область действия:** Автоматически применяется ко всем тестам (`autouse=True`), обеспечивая чистое состояние БД перед каждым тестом.
*   **Логика работы:**
    1.  Создает новое соединение с SQLite в оперативной памяти (`:memory:`).
    2.  Инициализирует полную схему БД (таблицы `users`, `cities`, `forecasts`) с теми же SQL-ограничениями, что и в продакшн-коде.
    3.  Подменяет зависимость `get_db` в экземпляре FastAPI через механизм `app.dependency_overrides`. Благодаря этому все эндпоинты в рамках теста используют именно это in-memory соединение.
    4.  После завершения теста (после `yield`) восстанавливает исходные зависимости и закрывает соединение, обеспечивая полную изоляцию.

### 2.2. Моки внешнего API (Open-Meteo)
Для эмуляции ответов внешнего сервиса используются предопределенные JSON-структуры и функции-заглушки:

*   **`MOCK_CURRENT_RESPONSE`**: Фиктивный JSON-ответ для эндпоинта текущей погоды (температура 15.5°C, ветер 10.2 км/ч, давление 1015 гПа).
*   **`MOCK_HOURLY_RESPONSE`**: Фиктивный JSON-ответ для почасового прогноза (2 часа данных с температурой, влажностью, ветром и осадками).
*   **`mock_open_meteo_current()`** и **`mock_open_meteo_hourly()`**: Функции, возвращающие `MagicMock`-объекты. Они имитируют поведение `httpx.Response`, корректно обрабатывая вызовы методов `.json()` и `.raise_for_status()`.

## 3. Подробное описание тестов

### Тест 1: `test_get_current_weather`
*   **Цель:** Проверка корректности парсинга и возврата данных текущей погоды.
*   **Механизм:** Подменяет `httpx.AsyncClient.get` моком `mock_open_meteo_current`. Выполняет GET-запрос к `/weather/current` с валидными координатами.
*   **Проверяемые утверждения (Asserts):**
    *   HTTP-статус `200 OK`.
    *   Температура, скорость ветра и давление в ответе в точности совпадают с моковыми данными.
    *   Внешний API был вызван ровно один раз (`mock_get.call_count == 1`).

### Тест 2: `test_register_user`
*   **Цель:** Проверка успешной регистрации нового пользователя.
*   **Механизм:** Отправляет POST-запрос к `/users/register` с валидным телом запроса.
*   **Проверяемые утверждения:**
    *   HTTP-статус `201 Created`.
    *   В ответе присутствует корректный `user_id` (1, так как БД пуста).
    *   Поле `username` в ответе совпадает с отправленным.

### Тест 3: `test_register_user_duplicate`
*   **Цель:** Проверка обработки ошибки при попытке регистрации с уже существующим именем.
*   **Механизм:** Дважды отправляет POST-запрос с одинаковым `username`.
*   **Проверяемые утверждения:**
    *   Второй запрос возвращает HTTP-статус `409 Conflict`.
    *   В поле `detail` ответа содержится сообщение о том, что имя уже занято.

### Тест 4: `test_track_city`
*   **Цель:** Проверка полного цикла добавления города в отслеживание (включая нормализацию имени).
*   **Механизм:**
    1.  Регистрирует пользователя.
    2.  Подменяет внешний API моком `mock_open_meteo_hourly`.
    3.  Отправляет POST-запрос к `/cities/track` с названием "London".
    4.  Напрямую проверяет содержимое БД через тестовое соединение.
*   **Проверяемые утверждения:**
    *   HTTP-статус `201 Created`.
    *   В таблице `cities` присутствует запись с **нормализованным** именем `"london"` (lowercase), привязанная к правильному `user_id`.

### Тест 5: `test_get_city_weather_at_time_filtered`
*   **Цель:** Проверка динамической фильтрации параметров в прогнозе (возвращаются только запрошенные метрики).
*   **Механизм:**
    1.  Регистрирует пользователя и добавляет город.
    2.  Вручную вставляет тестовую запись прогноза в БД на текущую дату (эмуляция работы фоновой задачи).
    3.  Выполняет GET-запрос, запрашивая только `temperature` и `wind_speed`.
*   **Проверяемые утверждения:**
    *   HTTP-статус `200 OK`.
    *   В ответе присутствуют запрошенные поля (`temperature_c`, `wind_speed_kmh`) с правильными значениями.
    *   В ответе **отсутствуют** незапрошенные поля (`humidity_percent`, `precipitation_mm`). Это критически важная проверка корректности динамического формирования ответа.

### Тест 6: `test_get_weather_invalid_time_format`
*   **Цель:** Проверка валидации формата входного параметра `time`.
*   **Механизм:** Отправляет GET-запрос с некорректным форматом времени `"1200"` (отсутствует двоеточие).
*   **Проверяемые утверждения:**
    *   HTTP-статус `400 Bad Request`.
    *   Валидация срабатывает до обращения к БД, что подтверждает правильный порядок проверок в коде (валидация входных данных приоритетнее бизнес-логики).
